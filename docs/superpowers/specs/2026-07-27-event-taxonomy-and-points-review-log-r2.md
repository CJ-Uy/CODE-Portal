# Event Taxonomy and Multi-Type Points Review Log - Round 2

1. **Severity: Important**
   **Spec sections attacked:** §3 partial unique index, §5 set-based reconciliation
   **Evidence:** §3 says to use `onConflictDoUpdate({ target: [...], targetWhere: eq(retentionRecords.source, "event_attendance") })`. This repository's atomic path requires pre-built Drizzle statements and calls synchronous `.run()` locally (`src/db/repositories/events.ts:139-159`). The installed versions are `drizzle-orm` 0.45.2 and `better-sqlite3` 12.10.0 (`package.json:52`, `package.json:55`). A local in-memory probe against those exact packages showed Drizzle can build `insert(...).select(...).onConflictDoUpdate(...)`, but the spec's exact `targetWhere: eq(retentionRecords.source, "event_attendance")` generated `ON CONFLICT ("retention_records"."event_id", ... ) WHERE "retention_records"."source" = ?`, and better-sqlite3 rejected it with `ON CONFLICT clause does not match any PRIMARY KEY or UNIQUE constraint`. The same statement succeeded when `targetWhere` was emitted unqualified as ``sql`source = 'event_attendance'` ``.
   **Finding:** The set-based statement shape is feasible, but the spec's exact Drizzle `targetWhere` recipe is wrong for SQLite partial-index matching. Copying it makes `setAwards` fail at runtime on the first reconciliation.
   **Concrete resolution:** Keep the Drizzle `insert(...).select(...).onConflictDoUpdate(...)` approach, but require an unqualified predicate for the conflict target, for example ``targetWhere: sql`source = 'event_attendance'` ``. Add the generated-SQL check already demanded by §7, and make the expected SQL part of the test assertion.

2. **Severity: Important**
   **Spec sections attacked:** §9 Plan B2/B3 split, §5 `setPoints` to `setAwards`
   **Evidence:** Plan B2 says repository and contracts replace `setPoints` with `setAwards`, while Plan B3 defers the event-detail award editor. The current UI imports `setPointsAction` (`src/app/portal/calendar/[eventId]/event-manage-panel.tsx:28-35`), reads `event.points` into local state (`src/app/portal/calendar/[eventId]/event-manage-panel.tsx:620-623`), and calls `setPointsAction(event.id, points)` (`src/app/portal/calendar/[eventId]/event-manage-panel.tsx:627-633`). The server action still calls `repositories.events.setPoints` (`src/app/portal/calendar/[eventId]/actions.ts:93-97`). The page passes `managed.points` into that panel (`src/app/portal/calendar/[eventId]/page.tsx:99-113`). The existing shared contract also exposes `setPoints`, not awards (`src/db/contract/events.ts:122-128`).
   **Finding:** B2 is not independently deployable as written. If B2 removes or renames `setPoints` but B3 UI is not shipped, the build or runtime path breaks. If B2 keeps the old UI but stops writing `crs_events.points`, the panel reads stale data after an award change.
   **Concrete resolution:** Make B2 carry a compatibility shim until B3 lands: keep `setPointsAction` and a repository-level `setPoints` wrapper that maps the single value to the Retention award and returns the old `{ updated }` shape, or move the minimum event-detail action/UI replacement into B2. Do not stop writing or reading compatibility data until no shipped UI reads `event.points`, unless the B2 UI is changed in the same stage.

3. **Severity: Important**
   **Spec sections attacked:** §2 authorization and last-flag guard, §5 `recordScan`
   **Evidence:** Current production attendance writes route through `events.recordScan`, which inserts attendance and a retention row together (`src/db/repositories/events.ts:450-485`); shared-dev scan also calls `repository.recordScan` (`src/server/internal/events.ts:122-125`) when that op is allowed. §5 says future `recordScan` derives retention rows from `event_point_awards` inside the batch. §5 validates active point types in `setAwards`, and §2 says the deactivate guard protects the last retention-bearing type, but the sample SQL only clears `counts_toward_retention` and does not show the `active = 0` case.
   **Finding:** Dropping the FK on `retention_records.point_type_id` is mostly covered for unknown IDs, but not for stale inactive IDs. An award can be valid when saved, then its point type can be deactivated. A later scan that joins only `event_point_awards` will still create new `retention_records` for an inactive type. The spec does not say whether that is intended, and it does not assign repository enforcement to either `recordScan` or the point-type deactivate mutator.
   **Concrete resolution:** Pick one rule and encode it in the repository. Either `recordScan` joins `point_types` and only awards active types, with reconciliation deleting or preserving old rows by explicit policy, or deactivating a point type refuses while active/future events still award it. The last-flag SQL also needs the actual `active = 0` conditional update, not only the flag-clearing example.

4. **Severity: Minor**
   **Spec sections attacked:** §1 fail-closed reversal
   **Evidence:** `canCreateType` currently falls open on missing rows (`src/db/repositories/eventTypeRules.ts:17-31`). Both calendar pages intentionally catch a failed `eventTypeRules.list()` and substitute `[]` (`src/app/portal/calendar/page.tsx:30-34`, `src/app/portal/calendar/[eventId]/page.tsx:24-33`). `CreateEventSheet` treats an empty allowed-type list as "no allowed types" and disables submit (`src/app/portal/calendar/create-event-sheet.tsx:80-83`, `src/app/portal/calendar/create-event-sheet.tsx:116-127`). Repository create/update are the real enforcement points (`src/db/repositories/events.ts:224-227`, `src/db/repositories/events.ts:283-293`).
   **Finding:** The fail-closed reversal is safe for repository enforcement, but not for callers that use `[]` as a degraded read-failure fallback. After the helper changes, a transient rules read failure or shared-dev unavailable repository changes from "show hardcoded options, repository decides" to "no type can be selected."
   **Concrete resolution:** In Plan A, distinguish "rules loaded and row missing" from "rules failed to load." Let the page fail visibly, pass an unavailable state to the form, or keep a temporary UI-only fallback that never bypasses repository validation. Do not feed `[]` into a fail-closed membership helper unless an empty type table is the intended truth.

5. **Severity: Minor**
   **Spec sections attacked:** §9 B2/B3 split, §4 projections
   **Evidence:** §4 says `reportBaseColumns` and `myHistory` row DTOs gain point-type metadata. §9 puts "the two projections" in B2, but the XLSX column is deferred to B3. The export route immediately feeds repository rows to XLSX builders (`src/app/api/reporting/export/route.ts:40-58`), and the builders type their inputs from the retention repository (`src/server/reporting/xlsx.ts:2`).
   **Finding:** Stopping after B2 is technically coherent if extra row fields are unused, but the stage boundary is muddy: B2 makes projections typed, while B3 makes the exported file actually show the new type. That is not a data break, but it weakens the "independently deployable" claim because users can download an export that still hides the metadata B2 claims to deliver.
   **Concrete resolution:** Either move the XLSX column into B2 with the projection work, or reword B2 as "repository projections only; visible export rendering lands in B3."

The local migration runner's transaction wrapper does not change this for the no-`REFERENCES` form (`src/db/migrate-local-sqlite.ts:46-58`); an in-memory better-sqlite3 check accepted the statement inside `BEGIN` and backfilled `pt_retention`.

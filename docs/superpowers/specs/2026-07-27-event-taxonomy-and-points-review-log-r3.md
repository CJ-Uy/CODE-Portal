# Event Taxonomy and Multi-Type Points Review Log - Round 3

Final scoped review of only the material changed after round 2.

## Findings

1. **Severity: Major**
   **Spec section:** Section 5 `setPoints` shim, Section 9 Plan B2
   **Evidence:** Section 5 defines `setAwards` as replacement semantics: replace `event_point_awards` rows, then delete attendance-source rows whose type is no longer awarded (`docs/superpowers/specs/2026-07-27-event-taxonomy-and-points-design.md:431-435`). The new shim says `setPoints(actor, eventId, points)` survives as a thin wrapper that maps one value onto the Retention award and returns the old `{ updated }` shape (`docs/superpowers/specs/2026-07-27-event-taxonomy-and-points-design.md:477-483`). The old panel still calls `setPointsAction(event.id, points)` (`src/app/portal/calendar/[eventId]/event-manage-panel.tsx:627-633`) and displays `Updated {result} attendee record(s).` (`src/app/portal/calendar/[eventId]/event-manage-panel.tsx:668-670`). Current `setPoints` returns attendee count, not changed award rows: it reads attendees at `src/db/repositories/events.ts:323-326` and returns `attendees.length` at `src/db/repositories/events.ts:345-346`.
   **Finding:** A literal "thin wrapper calls `setAwards([{ Retention }])`" implementation would erase every non-Retention award for the event because `setAwards` replaces the whole award set. That breaks the exact future-path case B2 introduces: `setAwards` exists while the old single-number panel is still live. The `{ updated }` compatibility value is also underspecified; if it becomes affected row count from multi-type reconciliation, the old panel will show a number that no longer means attendee records.
   **Concrete resolution:** Specify `setPoints` as a compatibility operation, not a whole-set `setAwards` alias: update, insert, or remove only the Retention award; preserve all other `event_point_awards`; reconcile only the Retention attendance rows affected by that wrapper; mirror Retention to `crs_events.points`; return the distinct attendee count expected by the old panel.

2. **Severity: Major**
   **Spec section:** Section 2 inactive point types, Section 5 reconciliation
   **Evidence:** Section 2 says inactive point types stop granting going forward and existing rows are preserved (`docs/superpowers/specs/2026-07-27-event-taxonomy-and-points-design.md:297-305`). Section 5 still says reconciliation deletes attendance-source rows whose `point_type_id` is no longer awarded (`docs/superpowers/specs/2026-07-27-event-taxonomy-and-points-design.md:431-435`). B3's event detail editor is described as "a row per active point type" (`docs/superpowers/specs/2026-07-27-event-taxonomy-and-points-design.md:499-500`), so a saved inactive award can disappear from the submitted active-only award set. Existing attendance rows are scoped by event, member, and source today (`src/db/repositories/events.ts:517-523`), so deletion scope is entirely repository-defined.
   **Finding:** The preserve-history rule conflicts with the no-longer-awarded deletion rule. Once a type is deactivated, a later `setAwards` from an active-only editor can drop that inactive award row; the Section 5 delete then removes historical rows that Section 2 says must survive. Separately, if a type is deactivated between `setAwards` validation and the set-based write, the event can retain an inactive `event_point_awards` row that grants nothing on future scans, with no required event-detail explanation.
   **Concrete resolution:** Define inactive-award semantics in the repository. Delete obsolete attendance rows only for active point types that were intentionally removed, or explicitly snapshot historical grants before deleting. Make `setAwards` re-check active status in the write path and fail on active-state drift, or make inactive awarded types visible as "retired, no longer grants" until removed by an explicit admin action.

3. **Severity: Major**
   **Spec section:** Section 1 three-state rules load
   **Evidence:** Section 1 calls out the two calendar pages and `CreateEventSheet` as needing a loaded-empty vs failed-load distinction (`docs/superpowers/specs/2026-07-27-event-taxonomy-and-points-design.md:205-223`). Actual source has a third current caller: `/portal/admin/system/event-types` catches `eventTypeRules.list()` failures to `[]` (`src/app/portal/admin/system/event-types/page.tsx:12-15`). Its manager maps every hardcoded type and treats a missing rule as `""` (`src/app/portal/admin/system/event-types/event-type-rules-manager.tsx:26-28`), where `""` renders as "Any member" (`src/app/portal/admin/system/event-types/event-type-rules-manager.tsx:47-53`). The action then writes that submitted value through the repository (`src/app/portal/admin/system/event-types/actions.ts:18-23`). In shared mode, `eventTypeRules` is a throwing Proxy (`src/db/repositories/index.ts:98-100`, `src/db/repositories/index.ts:117-120`).
   **Finding:** The revised three-state rule still misses the admin policy screen. A load failure or shared-dev Proxy throw is still mistaken for real empty rules there, and the UI presents all types as "Any member." That is worse than the create form outage because an admin can save the false default and overwrite actual policy.
   **Concrete resolution:** Add the event-types admin page to Plan A's three-state work. On failed load, render an unavailable state or let the page fail loudly; do not pass `[]` into `EventTypeRulesManager` unless the table was actually loaded and empty.

4. **Severity: Minor**
   **Spec section:** Section B, Section 5, Section 9 Plan B2
   **Evidence:** Section B still lists "`crs_events.points` is not dropped; it is deprecated and left unwritten" as a deliberate consequence (`docs/superpowers/specs/2026-07-27-event-taxonomy-and-points-design.md:50-55`). The round-2 revision later says it cannot stop being written while the old UI reads it (`docs/superpowers/specs/2026-07-27-event-taxonomy-and-points-design.md:468-486`) and Plan B2 ships the mirror because the old panel reads `event.points` (`docs/superpowers/specs/2026-07-27-event-taxonomy-and-points-design.md:580-585`). Actual source confirms the panel initializes from `event.points` (`src/app/portal/calendar/[eventId]/event-manage-panel.tsx:620-623`) and the page passes `managed.points` (`src/app/portal/calendar/[eventId]/page.tsx:98-113`).
   **Finding:** The spec still contains a stale factual instruction. "Left unwritten" contradicts the new B2 compatibility mirror and can send implementation in the exact wrong direction.
   **Concrete resolution:** Change Section B to: "`crs_events.points` is retained and deprecated; B2 writes it only as a compatibility mirror, B3 removes that write after no shipped UI reads it. Dropping the column remains deferred."

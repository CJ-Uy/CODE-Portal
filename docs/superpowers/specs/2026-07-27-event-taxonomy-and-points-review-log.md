# Event Taxonomy and Multi-Type Points Review Log

1. **Severity: Critical**
   **Spec sections attacked:** §1, §3, §5, §9, §10
   **Evidence:** Deployed code names and queries `event_type_rules` (`src/db/schema.ts:271`, `src/db/repositories/events.ts:224-227`, `src/db/repositories/events.ts:283-292`). It still writes `crs_events.points` (`src/db/repositories/events.ts:224-247`, `src/db/repositories/events.ts:319-333`) and inserts retention rows without `point_type_id` (`src/db/repositories/events.ts:469-485`, `src/db/repositories/retention.ts:240-255`). Remote migration and Worker deployment are separate commands (`package.json:15`, `package.json:31`).
   **Finding:** Both plans are migration-first incompatible with the currently deployed Worker. Plan A's table rename makes event creation and type-changing edits fail until the new Worker is live. Plan B's NOT NULL column makes old scan/manual writes fail, while dropping `crs_events.points` makes old event reads and writes fail. A failed or delayed deploy leaves beta broken after a successful migration.
   **Suggested resolution:** Use expand-contract releases. For Plan A, keep the physical `event_type_rules` name for now and add columns in place, or provide a compatibility object through the cutover. For Plan B, first add new tables and a nullable/defaulted `point_type_id` while retaining `crs_events.points`; deploy code that can read old data and dual-write/backfill; validate; only then enforce NOT NULL and consider legacy-column cleanup in a later migration. Every migration must remain compatible with the previous Worker.

2. **Severity: Critical**
   **Spec sections attacked:** §7, §9 Plan B
   **Evidence:** The local runner puts every migration inside `BEGIN`/`COMMIT` and already records that `PRAGMA foreign_keys=OFF` cannot take effect there (`src/db/migrate-local-sqlite.ts:11-13`, `src/db/migrate-local-sqlite.ts:46-58`). `crs_events` is the parent of cascade-deleting event staff, invites, RSVPs, attendance, media, and forum rows (`src/db/schema.ts:201-218`, `src/db/schema.ts:221-268`, `src/db/schema.ts:279-315`).
   **Finding:** "Any migration containing PRAGMA runs outside the transaction" is not a sound fix. It removes local atomicity, treats unrelated PRAGMAs identically, and still does not make a Drizzle `foreign_keys=OFF` rebuild portable to D1. More seriously, rebuilding the parent `crs_events` table with foreign keys enabled or merely deferred can execute its `ON DELETE CASCADE` actions when the old table is dropped, erasing event child data.
   **Suggested resolution:** Do not rebuild `crs_events` merely to remove an unused column. Leave `points` deprecated and unwritten for this release. If later cleanup is necessary, verify direct `ALTER TABLE crs_events DROP COLUMN points` against the exact D1 runtime and test every child-table row count. Use D1's `PRAGMA defer_foreign_keys=ON` only where a child-table rebuild actually needs it, and keep that migration transactional. Do not add generic PRAGMA detection to the local runner.

3. **Severity: Important**
   **Spec sections attacked:** §3, §5, §9 Plan B
   **Evidence:** Manual retention input has no point type (`src/db/types.ts:35-47`), its server action supplies only member, term, event, points, and reason (`src/app/portal/admin/data/retention/actions.ts:16-29`), and `createManual` inserts those fields directly (`src/db/repositories/retention.ts:230-255`). The repository also exposes a second unconditional retention-row writer, `recordEventAttendance`, with no point type (`src/db/repositories/retention.ts:37-43`, `src/db/repositories/retention.ts:70-76`, `src/db/repositories/retention.ts:122-138`).
   **Finding:** Plan B names `recordScan` but misses both retention repository write paths. After `point_type_id` becomes NOT NULL, the live manual-entry screen fails unless its whole contract is changed. `recordEventAttendance` also becomes invalid even if it is currently used only by tests.
   **Suggested resolution:** Add `pointTypeId` to the manual input schema, admin form, shared contract, repository type, and insert. Validate that the row exists and is active inside the repository. Either update `recordEventAttendance` the same way or remove the unused repository method and its obsolete tests. Do not silently default all future manual records to Retention unless that product rule is explicit.

4. **Severity: Important**
   **Spec sections attacked:** §5 `setPoints` to `setAwards`
   **Evidence:** `runAtomic` accepts already-built queries, using `db.batch` on D1 and synchronous `.run()` calls inside a local transaction (`src/db/repositories/events.ts:139-159`). Current `recordScan` performs reads before its atomic write batch (`src/db/repositories/events.ts:450-485`). Attendance already carries the original scanner and scan time (`src/db/schema.ts:254-268`).
   **Finding:** A JavaScript read of awards or attendees followed by per-row prepared writes is race-prone. A scan can read the old award set, a concurrent `setAwards` can commit, and the scan can then write stale per-type rows. The same pre-read gap can omit an attendee from reconciliation. The spec also leaves provenance undefined when a newly added award creates a row for an old attendance record.
   **Suggested resolution:** Reconcile with set-based SQL evaluated inside the atomic write: replace award rows, `INSERT ... SELECT` from `crs_attendance` joined to the final `event_point_awards`, upsert point values, then delete obsolete attendance-source rows. Generate new IDs in that statement and copy `crs_attendance.scanned_by`/`scanned_at` into new rows. Make `recordScan` derive its rows from `event_point_awards` inside the same batch as the attendance insert, not from a JavaScript snapshot.

5. **Severity: Important**
   **Spec sections attacked:** §3 partial unique index, §5 reconciliation
   **Evidence:** Existing `retention_records` has no uniqueness constraint over event/member/source (`src/db/schema.ts:350-373`). `recordEventAttendance` can insert repeated event-attendance rows without checking for an existing one (`src/db/repositories/retention.ts:122-138`).
   **Finding:** Creating the partial unique index can fail on existing duplicate production rows. After it exists, a normal `ON CONFLICT(event_id, member_id, point_type_id)` target does not match a partial index; SQLite requires the conflict target to carry the same `WHERE source = 'event_attendance'` predicate. Without that predicate, `setAwards` fails at runtime instead of upserting.
   **Suggested resolution:** Add a pre-migration duplicate query and an explicit abort or reviewed deduplication rule before creating the index. In Drizzle, use the three columns plus `targetWhere: eq(retentionRecords.source, "event_attendance")`, and test the generated SQL on both D1 and better-sqlite3. Also add a check that event-attendance rows require a non-null `event_id`.

6. **Severity: Important**
   **Spec sections attacked:** §2 guard, §6 point-types admin authorization
   **Evidence:** `retention:record` belongs to the retention role (`src/server/auth/permissions.ts:52-57`) and currently authorizes operational record entry and report access (`src/db/repositories/retention.ts:230-275`, `src/app/portal/admin/nav.ts:43-46`). The existing event-type mutator correctly repeats authorization and validation inside its repository rather than trusting its page/action (`src/db/repositories/eventTypeRules.ts:53-65`).
   **Finding:** `retention:record` is too broad for organization-wide point policy. A user intended to log records or export reports would be able to change which historical points determine every member's retained/probation status. The proposed "admin screen must refuse" last-flag guard is also bypassable by any other caller and race-prone when two admins clear different flagged types concurrently.
   **Suggested resolution:** Add `retention:configure` or use `role:assign` for point-type policy. Enforce it in every point-types repository mutator. Enforce the last retention-bearing type with one conditional SQL update inside the repository, covering both clearing `counts_toward_retention` and disabling the last usable retention type; check the affected-row count to report refusal.

7. **Severity: Important**
   **Spec sections attacked:** §1 runtime event types, §9 Plan A, "What already exists"
   **Evidence:** `canCreateType` explicitly treats a missing rule row as unrestricted, and `allowedEventTypes` is driven by the hardcoded tuple (`src/db/repositories/eventTypeRules.ts:17-35`). `events.create` and type-changing `events.update` rely on that helper (`src/db/repositories/events.ts:224-227`, `src/db/repositories/events.ts:283-293`). Today, Zod enums block unknown input (`src/app/portal/calendar/actions.ts:11-25`, `src/app/portal/calendar/[eventId]/actions.ts:16-33`). At the database layer, `crs_events.type` is plain `TEXT NOT NULL` with no CHECK or foreign key (`drizzle/migrations/0000_young_bullseye.sql:178-200`, `src/db/schema.ts:171-198`).
   **Finding:** Removing the enum before reversing the helper's missing-row behavior opens arbitrary event-type strings at the repository layer. The assertion that production rows contain exactly the three seeded values is also not enforced by the database, so "no event rows are migrated" is an assumption, not a verified migration fact.
   **Suggested resolution:** Make a missing type row fail closed. Validate key shape and length at Zod boundaries, then validate existence, active state, and required permission again in `events.create`/`events.update`. Before Plan A, query distinct `crs_events.type` values against the three seed rows and either abort on unknown values or create reviewed inactive placeholder rows. Define key generation and immutability for newly created types.

8. **Severity: Important**
   **Spec sections attacked:** §5 `setAwards`, §8 testing
   **Evidence:** The existing shared contract constrains one point value to an integer from -100 to 100 (`src/db/contract/events.ts:122-128`), but the direct server action passes its argument straight to the repository (`src/app/portal/calendar/[eventId]/actions.ts:93-98`). The browser's `min`/`max` is only client-side (`src/app/portal/calendar/[eventId]/event-manage-panel.tsx:647-660`), while `setPoints` itself checks authorization but not value validity (`src/db/repositories/events.ts:319-333`).
   **Finding:** The current repository already trusts a caller for point validity, and the proposed array signature specifies no replacement validation. Duplicate point-type IDs, non-integers, excessive values, unknown IDs, and inactive IDs are otherwise left to constraint failures or inconsistent behavior.
   **Suggested resolution:** Validate again inside `setAwards`: bounded array length, unique `pointTypeId`, integer points with the existing -100 to 100 range unless product explicitly changes it, and existing active point-type rows. Keep Zod validation at server/shared boundaries too, but do not treat it as the repository guard.

9. **Severity: Important**
   **Spec sections attacked:** §4 in-memory aggregation, §6 member breakdown
   **Evidence:** `myHistory` currently selects all rows, reduces them in memory, and returns the same raw rows (`src/db/repositories/retention.ts:339-366`). Its output record has no point-type field (`src/db/contract/retention.ts:5-15`, `src/db/contract/retention.ts:107-115`), and the UI renders only date, source, and an unlabeled number (`src/components/retention-history.tsx:69-85`).
   **Finding:** The §4 option to restrict the `myHistory` rows query to retention-bearing types conflicts with §6's promise of a full breakdown because it would remove Frontliner and other records from the returned history. Keeping all rows without expanding the DTO leaves every non-Retention number unlabeled. Adding `pointTypeLabel` only to `reportBaseColumns` does not fix this member path.
   **Suggested resolution:** Join point-type metadata into all record DTOs, including `retentionRecordOutputSchema` and `myHistory`. Return all rows for the breakdown, but reduce only rows whose joined type counts toward retention. Define whether `recordCount` means all typed rows, retention-bearing rows, or distinct activities, then test that exact meaning.

10. **Severity: Important**
    **Spec sections attacked:** §5 notification and audit ordering
    **Evidence:** Current `setPoints` commits event/retention changes first, then writes attendee notifications one at a time, then writes the audit entry (`src/db/repositories/events.ts:327-346`). Each notification and audit entry is a separate database insert that can throw (`src/db/repositories/notifications.ts:55-63`, `src/db/repositories/audit.ts:46-60`).
    **Finding:** The proposed order preserves an existing partial-failure bug. One notification failure can leave awards fully changed, some attendees notified, later attendees unnotified, and no audit entry. "Notify attendees once" is not an atomic or retry-safe guarantee under this structure.
    **Suggested resolution:** Put the audit insert in the same atomic unit as award and retention reconciliation. Treat notification fan-out as explicitly best effort with all recipients attempted and failures recorded, or add an outbox if durable exactly-once delivery is a real requirement. Do not claim atomic notification semantics without one of those mechanisms.

11. **Severity: Minor**
    **Spec sections attacked:** §4 "The six aggregations", §8 testing
    **Evidence:** The actual total/status calculations are the four sites in retention (`src/db/repositories/retention.ts:162-188`, `src/db/repositories/retention.ts:191-227`, `src/db/repositories/retention.ts:339-364`) plus overview (`src/db/repositories/overview.ts:43-55`). `statusFor` is fed only by the two member-summary totals (`src/db/repositories/retention.ts:91-95`, `src/db/repositories/retention.ts:180-188`, `src/db/repositories/retention.ts:356-364`). `reportBaseColumns` selects individual rows rather than aggregating them (`src/db/repositories/retention.ts:107-118`), and the implemented file exports are XLSX only (`src/server/reporting/xlsx.ts:22-54`, `src/app/api/reporting/export/route.ts:40-58`).
    **Finding:** Exhaustive source search found no seventh points total or missed retained/probation computation. The risk list is complete, but its name is inaccurate: it contains five aggregations plus one untyped report/export projection, not six aggregations, and there is no CSV exporter in the current code.
    **Suggested resolution:** Rename the section and test matrix to "five totals/status reads plus typed report and history projections." Keep the retention filter on the five totals, add type metadata rather than a retention filter to full-detail exports, and test both XLSX builders.

12. **Severity: Minor**
    **Spec sections attacked:** §9 two plans
    **Evidence:** The retention repository does not import or call the event-type repository (`src/db/repositories/retention.ts:1-9`), while event-type policy is isolated in its own repository (`src/db/repositories/eventTypeRules.ts:1-15`). Plan B nevertheless touches the event repository's award update, scan path, notifications, retention rows, reports, contracts, and member status calculations (`src/db/repositories/events.ts:319-346`, `src/db/repositories/events.ts:450-485`, `src/db/repositories/retention.ts:107-227`, `src/db/repositories/retention.ts:339-366`).
    **Finding:** Plan A first is sensible product ordering, but the claimed hard technical dependency is not present; Plan B only benefits from copying its admin-screen pattern. Plan B is too broad for one safe migration-and-deploy pass because it combines destructive schema work, compatibility cutover, concurrency-sensitive writes, all retention totals, exports, and several UIs.
    **Suggested resolution:** Keep Plan A first for product value. Split Plan B into B1 additive schema/backfill and migration verification, B2 repository/contract dual-write plus reconciliation and aggregation tests, and B3 UI rollout and later legacy cleanup. Each stage should be deployable and rollback-compatible on its own.
